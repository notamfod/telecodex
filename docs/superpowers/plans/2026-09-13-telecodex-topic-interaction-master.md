# TeleCodex Topic Interaction Master Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to execute approved work packets task-by-task. Steps use checkbox (`- [ ]`) syntax. User authorized saving the plan and starting implementation on 2026-09-13. Commit, publication and service restart remain separate.

**Goal:** Сделать ежедневную работу с задачами через Telegram-топики понятной: найти задачу, восстановить контекст, увидеть состояние, выполнить следующее действие и получить результат.

**Architecture:** Топик остаётся основным местом переписки и управления конкретной задачей. Mini App обеспечивает поиск и обзор; оба интерфейса используют существующие canonical job projections и проверки действий. Жизненный цикл пользовательской задачи хранится отдельно от выполнения отдельных прогонов агента и доставки сообщений.

**Tech Stack:** TypeScript, grammY, SQLite/better-sqlite3, Codex app-server, Svelte 5, Carbon, Vitest, браузерные проверки с подменёнными API.

## 3. Решения по взаимодействию

1. Одна пользовательская задача имеет устойчивую идентичность и основной топик. Замена сессии агента не должна молча подменять смысл задачи.
2. В каждом подключённом рабочем топике одна карточка задачи, доступная через закреп. Технический per-job status anchor сохраняет собственную идентичность; карточка задачи не подменяет его в delivery ledger.
3. Карточка показывает цель, проект, состояние, последнее подтверждённое событие, ссылку на результат и доступные действия. Заполнение карточки не запускает дополнительный LLM-прогон.
4. Названия кнопок описывают результат действия. «Остановить прогон», «Завершить задачу» и «Повторить доставку» имеют разные последствия.
5. Завершение ответа агента обновляет результат; завершение задачи выполняется отдельным действием пользователя.
6. Ожидание ответа или разрешения не обозначается как зависание. Если ответ доступен только в другом клиенте, кнопка ведёт туда; нативный ввод разрешений не обещается без отдельного контракта app-server.
7. «Закрыть топик» означает закрытие для переписки, а не удаление или исчезновение из списка Telegram. Архив в Mini App является фильтром приложения.
8. При неопределённом результате отправки/создания показывается неопределённость. Таймаут не становится основанием для повторного создания топика или запуска агента.
9. Ручное название имеет приоритет над автоматическим. Статусы не вызывают частое переименование топиков; их основной носитель - карточка.
10. Dashboard-топик остаётся компактным обзором с входом в Mini App. Контекстные действия размещаются в рабочих топиках и карточках Mini App.

Пример карточки, иллюстрация целевого поведения:

```text
MIR-7097 · Одноразовый промокод
Проект: MirCli
Нужен твой ответ
Сделано: диагностика завершена
Дальше: выбрать вариант исправления
[К вопросу] [Последний результат] [Действия]
```

## 4. Разделение состояний

Предлагаемый контракт пользовательского представления; типы ниже новые, не существующие API:

```ts
type TaskLifecycle = "open" | "completed";
type AgentPresentation =
  | "idle" | "accepted" | "queued" | "running"
  | "needs_input" | "needs_approval" | "stalled"
  | "delivering" | "result_ready" | "failed" | "unknown";
type TopicPresence = "open" | "closed" | "missing" | "unknown";
```

`TaskLifecycle` отражает намерение пользователя, `AgentPresentation` вычисляется по текущему прогону и доказательствам доставки, `TopicPresence` отражает известное состояние Telegram. Отсутствие свежего наблюдения означает `unknown`, а не `missing`.

Существующие `TelegramStatusAction` передаются без потери `jobId`, `expectedVersion`, `partKey` и `alertId`. Завершение задачи и открытие топика имеют собственную версию операции; их нельзя кодировать как `abort` или `retry_new_turn`.

## 6. Проверки каждого выпуска

Последовательность work packet: добавить regression test -> получить ожидаемый RED -> минимальное изменение -> GREEN -> ревью изменённых сценариев -> полные проверки. Проверки строк исходника не заменяют проверку клика, состояния и сетевого запроса.

Команды локальной проверки в worktree; конкретные focused tests перечисляются в work packet:

```bash
TMPDIR=/var/tmp npm test -- --maxWorkers=1 --minWorkers=1
npm run check:web
TMPDIR=/var/tmp npm run build
git diff --check
```

В `package.json` пока нет отдельной lint-команды. Не писать «lint прошёл», если выполнены только typecheck и тесты. Сборку в каталоге работающего сервиса проводить с отдельными `--outDir`, чтобы не заменять его `dist`/`dist-web` во время диагностики.

Минимальная матрица: мобильные viewport 390x844 и 320x640, desktop keyboard, светлая/тёмная тема, offline/401/429, устаревший callback, двойной клик, restart, закрытый/удалённый/неизвестный топик. Подменять Telegram/API в автоматических тестах. Реальное мобильное взаимодействие проверять отдельно на согласованных тестовых топиках.

- [ ] Проверить сохранение topic/thread/card ID, отсутствие дублированных отправок и повторных запусков, health и свежие ошибки после перезапуска.
- [ ] Commit/push и deployment выполнять только по отдельному указанию; рекомендуемый формат commit: `NO-TICKET fix: ...` или `NO-TICKET feat: ...`.

Измеримые критерии приёмки программы, целевые значения, а не уже измеренный эффект:

| Сценарий | Цель |
| --- | --- |
| Открыть нужный топик из найденной карточки | Одно явное нажатие без свайпа |
| Увидеть завершение прогона | Актуальный список на следующем успешном обновлении |
| Повторить неудачную загрузку | Один клик, один запрос, видимый исход |
| Вернуться к задаче через несколько дней | Цель, состояние и последний результат доступны из закрепа |
| Найти известный тикет среди 200 задач | До 10 секунд в ручном сценарии поиска |
| Завершить и продолжить задачу | Тот же топик и сессия, без неявного запуска агента |
| Перезапустить бот | Сохранены привязки, карточки и незавершённые операции |
| Принять сообщение в Inbox | Есть сохраняемое состояние, итог либо явная неопределённость |
